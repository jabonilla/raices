# K3.2: Raíces threat and abuse model

Scope: main `04b64f6`, examined 2026-09-29. This is a technical and product review, not a claim that future PRD features are implemented. Existing API serves health/readiness/OpenAPI; current domain includes users, relationships, audit, posting and reconciliation. OTP, approval thresholds, production settlement and channels are not yet wired. Recommendations require owner decisions; none changes product rules.

## Assets and boundaries

Protect approval authority, ledger integrity, account/relationship membership, phone/name/amount privacy, immutable history and a participant's ability to leave safely. Boundaries are shared sender/recipient devices → API or WhatsApp/SMS provider → authenticated actor → relationship-scoped domain → serializable DB/audit → settlement adapter. CI and database owner credentials sit above application permissions. The AI boundary is a pre-rendered, read-only context; it must never gain DB or write tools.

Assume attackers include an outside spammer, a compromised phone or channel account, an abusive authorized family member, compromised API or CI credentials, a malicious dependency and a dishonest settlement provider. A legitimate participant can still misuse the product. A database owner can disable triggers; append-only protection is not protection against unrestricted administrative power.

## Scenarios, present controls and recommended response

No implemented coercion escalation. | Provide private escalation from each channel; explain approval limits honestly; safety-test decline/termination copy with recipients; avoid framing control as consent. Emergency flags must not promise delivery. | Jose + product + operations; before real-money pilot |
| Recipient is pressured to request for someone else, or a third party dictates the category/story. | Structured relationship and immutable audit can record activity but cannot establish voluntary consent. | Do not infer consent from an authenticated click. | Replayed approval or malformed posting creates duplicate money impact. | Posting canonical hash, unique key, SERIALIZABLE retries, DB currency and balance checks; eight-way conflicting races tested. Approved-request path not present. | Preserve actor-scoped idempotency and atomic approval/ledger writes when implemented. Exercised gap: app can append balanced legs to a committed transaction; ledger owner must freeze membership. | Ledger/domain owner; high |
| Settlement partner lies about success, changes fees/FX, partially pays or replays a webhook. | Interface plus mock and append-only provider statements; reconciliation separates intent from settlement. Real provider integration absent. | Authenticate ingress, dedupe provider references, reconcile independent statement data, preserve partial/reversal records, explicit alerts and kill switch. Never let partner state rewrite intent or erase ledger entries. Model capabilities, not partner names. | Settlement owner + K0 |
| PII leaks into logs/spans/error responses, including attacker-controlled request IDs. | Key deny-list handles plain nested data. Free strings, class instances, request IDs, error serializers and span status are separate exposure paths. Span status leak exercised. | Allow-list telemetry fields; opaque server-generated correlation IDs; never log raw OTPs/tokens/body/errors carrying PII. Audit exporter and sink behavior. Redaction is insufficient for values under arbitrary keys. | Platform owner + K3 secrets review |
| Credential stuffing, OTP brute force, invite spam, phone enumeration. | Main has IP rate limiting with `trustProxy: true`; invite/auth routes absent. Trust boundary depends on deployment preventing direct ingress. | Persistent phone and trusted-IP limits, single-use short-lived codes, audited lockouts, indistinguishable account-existence errors and response shapes. Measure timing distributions; test forged forwarded headers. Do not claim constant total HTTP timing merely because digest comparison is constant-time. | K3 identity/HTTP + deploy owner |
| Compromised app process directly changes DB state or counterfeits audit. | App cannot mutate ledger/audit rows, but can insert audit and update relationship rows. Audit identifiers restrict shape, not meaning or actor truth. | Least privilege, separate credentials for migration and runtime, enforce state rules at DB/domain seam, review direct SQL exposure. Audit is a consistency record, not cryptographic proof against an attacker who controls the writer. | K0 + domain owner |

Mobile bundle is public to its device owner: never put privileged keys inside it. | Platform owner; K3.9 recommendations |
| AI prompt injection requests a balance, fabricates payout guarantees or tells tools to transfer. | PRD mandates read-only pre-rendered context and deterministic refusals; no production AI integration visible. | Give AI no DB or write permissions and no arbitrary context query. Exact approved values only; deterministic refusals for absent data. Run the specified held-out Spanish adversarial evaluation before deployment. | AI owner + Jose |

## Abuse response decisions still needed

1. Who receives coercion reports, during what hours, with what fallback? How can they contact a recipient without exposing the report on a shared device?
2. What history remains visible after termination when visibility itself creates danger? PRD currently promises retained history to both; do not silently change it.
3. How is a changed/recycled number linked to the previous person? Possession of the new number alone cannot establish this.
4. What notification copy is safe when the person holding the phone is the adversary? No names or amounts on lock-screen previews.
5. What thresholds require independent step-up and what recovery can bypass it? K0/Jose must decide; the implementation must not invent them.
6. Who can suspend partner instructions or compromised sessions, and what append-only evidence is retained? Define the incident workflow before real transfers.

## Verification and residual risk

K3.1 exercised real DB contention, mutation and money properties and confirmed three regressions. This document's other scenarios are analysis or planned requirements, not penetration-test results. Authentication, channel signatures, real settlement, coercion response and launch thresholds remain independently reviewable gates. Production changes by K3 require K0 review even when tests pass. The public repository must not receive unapproved detailed vulnerability disclosures.
